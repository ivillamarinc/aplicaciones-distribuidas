\begin{abstract}
Este trabajo presenta el diseño de la arquitectura de microservicios del sistema TiendaTech empleando el modelo de diagramas C4 en su nivel 3 (componentes). Se identifican las responsabilidades de cada microservicio, los mecanismos de comunicación síncrona y asíncrona, así como las tecnologías necesarias para la integración y operación del sistema distribuido. El diseño propone una separación de responsabilidades que facilita la escalabilidad y el mantenimiento, combinando REST y RabbitMQ para equilibrar la rapidez de respuesta con el desacoplamiento entre servicios.
\end{abstract}

\begin{IEEEkeywords}
Microservicios, C4 Nivel 3, API Gateway, RabbitMQ, REST, PostgreSQL, arquitectura distribuida.
\end{IEEEkeywords}

% -------------------------------------------------------
\section{Introducción}

El diseño de sistemas distribuidos mediante arquitecturas de microservicios ha cobrado gran relevancia en el desarrollo de aplicaciones modernas. Este paradigma propone descomponer una aplicación monolítica en servicios pequeños, autónomos e independientemente desplegables, cada uno con una responsabilidad bien definida \cite{newman2015}.

El presente trabajo describe la arquitectura del sistema TiendaTech, una plataforma de comercio electrónico diseñada bajo el enfoque de microservicios. Para su modelado se utiliza el diagrama C4 en su nivel 3, que describe los componentes internos de los contenedores del sistema y sus interacciones.

El repositorio del proyecto se encuentra disponible en: \url{https://github.com/ivillamarinc/aplicaciones-distribuidas}

\section{Objetivo}

Diseñar la arquitectura de microservicios del sistema TiendaTech mediante un diagrama C4 nivel 3, identificando responsabilidades, mecanismos de comunicación síncronos y asíncronos, así como las tecnologías necesarias para la integración y operación del sistema distribuido.

% -------------------------------------------------------
\section{Descripción de la Arquitectura}

La arquitectura propuesta sigue el principio de responsabilidad única (SRP) y está compuesta por los siguientes elementos principales:

\subsection{Frontend Web TiendaTech}
Interfaz desarrollada con HTML, CSS y JavaScript que permite al usuario interactuar con el sistema. Envía todas las solicitudes al API Gateway como punto de entrada centralizado.

\subsection{API Gateway}
Implementado con Spring Boot y Spring Cloud Gateway, constituye el único punto de acceso al sistema. Gestiona la autenticación, autorización y el enrutamiento de solicitudes hacia los microservicios correspondientes.

\subsection{Microservicio de Usuarios}
Construido con Spring Boot, REST y JWT. Gestiona el registro de usuarios, inicio de sesión, autenticación JWT y recuperación de credenciales. Dispone de su propia base de datos PostgreSQL denominada \textit{BD Usuarios}.

\subsection{Microservicio de Productos}
Implementado con Spring Boot y REST. Administra el catálogo de productos, incluyendo categorías, imágenes, búsquedas, precios, detalles y control de inventario disponible. Persiste su información en la \textit{BD Productos}.

\subsection{Microservicio de Carrito}
Desarrollado con Spring Boot y REST. Gestiona los productos agregados al carrito, actualiza información de productos y calcula los totales previos a la compra. Utiliza la \textit{BD Carrito} para almacenar los estados activos de compra.

\subsection{Microservicio de Pedidos y Facturación}
Construido con Spring Boot y REST. Gestiona la creación de pedidos, facturas y el historial de compras. Publica eventos hacia la cola de mensajes indicando que un pedido ha sido creado. Consume eventos de pago para actualizar el estado del pedido. Se apoya en la \textit{BD Pedidos y Facturación}.

\subsection{Microservicio de Pagos}
Implementado con Spring Boot, REST y la API de PayPal. Procesa los pagos utilizando PayPal, obtiene el estado de disponibilidad y registra el estado de cada transacción. Publica eventos de pago confirmado o rechazado hacia la cola de mensajes. Utiliza la \textit{BD Pagos}.

\subsection{Cola de Mensajes}
Implementada con RabbitMQ. Distribuye y enruta eventos entre microservicios de forma asíncrona sin necesidad de esperar una respuesta inmediata, garantizando el desacoplamiento entre los servicios productores y consumidores.

% -------------------------------------------------------
\section{Comunicación y Tecnologías}

\subsection{Comunicación Síncrona}

La comunicación síncrona se realiza mediante el protocolo HTTP REST con intercambio de datos en formato JSON. Este mecanismo se emplea para las operaciones que requieren una respuesta inmediata, tales como:

\begin{itemize}
    \item Solicitudes del Frontend al API Gateway.
    \item Enrutamiento del API Gateway hacia los microservicios de Usuarios, Productos y Carrito.
    \item Registro de pedidos y facturas desde el API Gateway hacia el microservicio de Pedidos y Facturación.
    \item Procesamiento de pagos desde el API Gateway hacia el microservicio de Pagos.
\end{itemize}

\subsection{Comunicación Asíncrona}

La comunicación asíncrona se implementa mediante RabbitMQ. Este mecanismo permite el intercambio de eventos sin bloquear el flujo principal de ejecución, siendo utilizado en los siguientes escenarios:

\begin{itemize}
    \item Publicación del evento \textit{pedido\_creado} por parte del microservicio de Pedidos y Facturación.
    \item Consumo del evento de pago por parte del microservicio de Pedidos para actualizar el estado del pedido.
    \item Publicación del evento de pago confirmado o rechazado por parte del microservicio de Pagos.
\end{itemize}

\subsection{Tecnologías Utilizadas}

Las tecnologías empleadas en la arquitectura se resumen a continuación:

\begin{itemize}
    \item \textbf{Spring Boot / Spring Cloud Gateway:} desarrollo de microservicios y API Gateway.
    \item \textbf{REST / JSON:} comunicación síncrona entre componentes.
    \item \textbf{JWT:} autenticación y autorización de usuarios.
    \item \textbf{RabbitMQ:} mensajería asíncrona basada en eventos.
    \item \textbf{PostgreSQL:} almacenamiento independiente para cada microservicio.
    \item \textbf{PayPal API:} procesamiento de pagos externos.
    \item \textbf{HTML, CSS, JavaScript:} desarrollo del Frontend Web.
\end{itemize}

\section{Retroalimentación y Mejoras}

Durante la revisión del diseño inicial se identificó la ausencia de mecanismos de comunicación asíncrona y la falta de diferenciación explícita entre los tipos de interacción entre servicios. Como resultado de esta retroalimentación se realizaron las siguientes mejoras:

\begin{enumerate}
    \item Incorporación de RabbitMQ como componente de mensajería asíncrona basada en eventos.
    \item Identificación y etiquetado explícito de las comunicaciones síncronas (\textit{sync}) y asíncronas (\textit{async}) dentro del diagrama C4.
    \item Definición clara de los eventos publicados y consumidos por cada microservicio.
\end{enumerate}

Estas mejoras contribuyen a un diseño más robusto, flexible y alineado con las buenas prácticas de arquitecturas orientadas a eventos.

% -------------------------------------------------------
\section{Análisis y Discusión}

La arquitectura propuesta sigue los principios fundamentales del diseño de microservicios \cite{fowler2014}: separación de responsabilidades, independencia de bases de datos por servicio y comunicación bien definida entre componentes.

El uso del patrón API Gateway centraliza la autenticación y el enrutamiento, simplificando la interacción del Frontend con el sistema sin necesidad de conocer la topología interna de los servicios \cite{richardson2018}.

La combinación de REST para operaciones síncronas y RabbitMQ para comunicación asíncrona permite equilibrar la latencia de respuesta en operaciones críticas (consulta de productos, autenticación) con la desconexión temporal requerida en flujos de mayor complejidad (creación de pedidos, notificación de pagos).

Sin embargo, la arquitectura distribuida incrementa la complejidad operativa al requerir mecanismos adicionales de coordinación, monitoreo, gestión de fallos y consistencia eventual entre los microservicios.

% -------------------------------------------------------
\section{Conclusión}

La arquitectura de microservicios diseñada para TiendaTech organiza el sistema en servicios independientes que facilitan la escalabilidad y el mantenimiento de la plataforma. La separación de responsabilidades mejora la flexibilidad del sistema, aunque también incrementa la complejidad operativa al requerir mecanismos adicionales de coordinación, monitoreo y gestión de comunicaciones.

El uso combinado de REST y RabbitMQ resulta necesario y adecuado para equilibrar la rapidez de respuesta con el desacoplamiento entre los microservicios. La adopción del modelo C4 nivel 3 como herramienta de documentación arquitectónica facilita la comprensión del sistema por parte de todos los involucrados en su desarrollo y mantenimiento.
